## 0. 30 秒电梯稿

> 把一门企业内部培训课程变成可自动考核的系统：管理员上传培训资料（PDF/Word/Markdown），
> 系统解析入库；发布考核后，员工点"开始考核"时基于该资料用 RAG 实时生成一套**只属于他个人**的题目，
> 答完自动判分并生成复盘报告。技术上是一个 FastAPI + aiomysql 的后端、Vite + React 19 + AntD 6 的前端，
> AI 侧用 LangChain/LangGraph 编排 ReAct Agent 做检索，模型走阿里云百炼与 DeepSeek，
> 用 Docker Compose 部署在阿里云 ECS 上，Nginx 反代。

## 1. RAG 自动出题链路

### 1.1 数据流全景

```
上传文件
  routes/knowledge.py → knowledge_service.handle_upload        (services/knowledge_service.py:32)
    校验扩展名/大小/每人≤10篇 → 生成 doc_{uuid12} → 落盘 → DB 插记录 status='processing'
    → asyncio.create_task(_process_document) 立即返回            (:67)

_process_document (异步，:72-93)
  document_loader_service.load_and_split
    pdf=PyPDFLoader(按页) / docx=Docx2txtLoader / md,txt=TextLoader   (document_loader_service.py:17-36)
    RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=150)
      值来自 core/config.py:28-29（kb_chunk_size/kb_chunk_overlap，可被入参覆盖）
      应用于 document_loader_service.py:49-56
  vector_store_service.add_document_chunks
    OpenAIEmbeddings + 百炼 text-embedding-v4 (compatible-mode)        (vector_store_service.py:17-33)
    ChromaDB collection = kb_user_{user_id}，metadata 注入 doc_id/user_id (:36-45, :60-65)
  update_document_status('ready', chunk_count)  异常→'failed' + error_message[:500]

员工点「开始考核」
  assessment_service.start_assessment                                (assessment_service.py:106-135)
    → quiz_service.handle_quiz_generate(doc_owner_id=created_by)
       _fetch_context → rag_service.fetch_rag_context                 (rag_service.py)
         create_react_agent(工具=向量检索 + 可选联网)  ← Agentic RAG   (:39-92)
       → llm/quiz_chain.generate_quiz  裸 LCEL: prompt | llm           (quiz_chain.py:24-64)
       → 题目落库，quiz_id 归该员工

提交
  判分：纯规则，零 LLM   sorted(所选)==sorted(答案)                    (assessment_service.py:151-162)
  报告：唯一一次 LLM 调用，输入=题目+作答+统计                          (llm/report_chain.py:21-52)
```

### 1.2 三个能体现思考深度的决策

**① Agentic RAG，而不是"一次向量检索塞进 prompt"**

向量检索被封装成**工具**交给 ReAct Agent（`rag_service.py:39-92`），让模型自己判断
"知识库检索到的内容够不够出题"，不够才追加检索或联网补充（`prompts/rag_prompt.py:14-18`，工具调用硬上限 3 次）。

- 收益：资料稀疏或问题跨章节时，模型可以多轮检索而不是被一次 top_k 结果限死
- 代价：**多一次 LLM 往返**，延迟和 token 都涨
- 所以我加了护栏：`recursion_limit=10`、**60s 超时**、结果截断 3000 字，
  失败或超时**返回空串降级**（`:139-148`）——宁可出"无参考资料"的题，也不能让检索把整个出题流程拖死

> 面试话术：「这里我做了个取舍。朴素 RAG 一次检索就完事，但我希望资料不足时模型能主动补检索，
> 所以做成 Agentic。代价是多一次 LLM 往返，所以必须配超时和降级，否则用户点开始考核会卡死。」

**② 题目在"开始考核"时生成，不在发布考核时生成**

`create_assessment`（`:49-68`）只存元数据（doc_id、题量、难度、及格线），**不生成题**；
真正的生成发生在 `start_assessment`（`:115`）。

- 结果：**每个员工拿到的是独立的一套题**（quiz_id 新生成、落库归员工 `quiz_service.py:113-122`）
- 为什么：这是考核系统，同套题会被传答案。每人一套天然防串题
- 代价：首个员工等待时间长（要现生成），且无法预知题目质量

**③ 判分绝不让 LLM 参与**

`is_correct = sorted(selected) == sorted(question.answer)`（`assessment_service.py:151-162`），
标准答案存在服务端 `questions_json` 里，前端拿不到。

- 理由：判分是**确定性计算**，交给 LLM 只会引入不稳定、成本和被篡改风险
- 多选要求全对（`sorted` 比较天然实现），判断题固定 A正确/B错误（`prompts/quiz_prompt.py:15`）
- LLM 只在最后生成复盘报告时用一次，输入是题目+作答+统计摘要（`report_chain.py:38-49`）

> 面试话术：「我的原则是能用规则做的绝不用 LLM。判分是精确比较，LLM 做只会更慢更贵还不稳定；
> LLM 的价值在理解语义，所以放在生成题目和写复盘建议这两处。」

### 1.3 必须主动承认的不足（被追问时不慌）

| 不足 | 现状 | 怎么改 |
| --- | --- | --- |
| 分块不感知结构 | Markdown 也走 TextLoader + 固定 1000/150 字符切（`core/config.py:28-29`），会把"数据分级表格"从中间切断 | 按标题层级切（MarkdownHeaderTextSplitter），或标题+递归二级切分 |
| 检索无阈值无 rerank | `top_k=4` 写死（`core/config.py:30`），不判相似度下限，垃圾片段也会进 prompt | 加 relevance score 阈值 + 轻量 rerank；top_k 按文档长度自适应 |
| LLM 输出无重试 | 四层兜底（prompt 禁 markdown（`prompts/quiz_prompt.py:3`）→ 正则剥 ```json 壳 `quiz_chain.py:19` → Pydantic `Literal` 硬校验 → 包业务异常），但**一次失败就报错** | `with_structured_output` + `with_retry`，或开 json_mode |
| 异步任务无队列 | `asyncio.create_task` 进程内 fire-and-forget，进程重启会残留 `processing` 僵尸文档 | 上 Celery/RQ；或启动时扫描超时 processing 重跑 |
| 报告失败会连带提交失败 | `submit_assessment:168` 没包 try，报告 LLM 挂 → 整次提交 500，成绩也丢了 | 成绩先落库再异步生成报告（小程序侧 `report_service.py:16-64` 已是这个写法） |
| assessments.doc_id 无外键 | 管理员删文档会留悬空引用，员工点开考核才报错 | 加 FK 或删除时级联关闭关联考核 |

## 2. 认证与权限：bcrypt + JWT + RBAC

### 2.1 口令存储

`app/core/password.py` 直接用 `bcrypt`，`ROUNDS = 12`，**没用 passlib**。

- 为什么不用 passlib：passlib 与 bcrypt≥4.1 有已知的 `version read error` 兼容问题，
  且它是个抽象层，本项目只需要一个哈希函数
- 为什么 cost=12：本机实测（bcrypt 5.0.0）`hash_password` 198ms、`verify_password` 197ms。
  登录是低频操作，200ms 用户无感，但离线爆破的成本被抬高约 4 倍（相对 cost=10），
  这是「拖慢攻击者」与「不拖慢用户」之间的平衡点
- 哈希产物格式可以背：`$2b$12$` 开头、总长 60 字符——排障时靠这个判断哈希是不是本项目生成的
- `users.status` 是 **TINYINT 整数 1**，不是字符串（`db.py:25`）——踩过坑，见 §3

### 2.2 三层守卫

```
第一层 后端依赖注入（真正的安全边界）
  get_current_web_user   解 JWT → 查库 → 校验账号存在 + status==1     (auth.py:74-85)
  get_current_admin      在上面基础上校验 role=='admin'，否则 403      (auth.py:88-93)
  所有 /admin/* 路由 Depends(get_current_admin)                       (routes/admin.py)

第二层 前端路由守卫（只是体验优化，不是安全）
  RequireRole 未 ready 显示 loading；未登录跳 /login 并记住来源路径；
  角色不符跳到该角色首页                                              (RequireRole.tsx:9-22)

第三层 数据层租户隔离
  JWT payload 只放 user_id/role，接口一律从 token 取身份，不接受前端传 user_id
```

> 面试话术：「前端路由守卫只是不让员工看到不该看的页面，真正的鉴权在后端依赖里。
> 我特意让 `RequireRole` 处理 `ready` 这个状态——因为刷新页面时要等 `/auth/me` 回来才知道身份，
> 否则会闪一下再跳登录页。」

### 2.3 这个项目最有意思的设计：双身份分离

场景：资料是**管理员**上传的，但考核是**员工**在答。
员工点开始考核时，系统要去检索管理员的文档——但按租户隔离规则，员工查不到管理员的文档。

如果直接放开查询条件就成了越权漏洞。我的做法是**把两个身份拆开传**：

```python
# quiz_service.py:87  注释原文：资料归属管理员、答题会话归属员工，二者分离
owner_id = doc_owner_id if doc_owner_id is not None else user_id
```

- `owner_id` **只**用于两件事：校验文档存在且 ready（`_validate_doc_id:55-68`）、
  决定去哪个 `kb_user_*` collection 检索（`_fetch_context:71-75`）
- 落库、判分、成绩归属**仍然用 user_id**（员工自己）
- 调用方 `assessment_service.py:124` 传 `doc_owner_id=assessment.get("created_by")`，
  而这个 `created_by` 来自服务端记录的考核创建者，**不是前端能伪造的参数**

隔离本身是双保险：向量层 collection 名 `kb_user_{id}` + `doc_id` filter
（`vector_store_service.py:42,95`），关系层 SQL 再强制 `AND user_id=%s`（`knowledge_repository.py:57-61`）。

> 面试话术：「这个设计的要点是——我需要一个受控的跨租户读，但不能开一条通用的后门。
> 所以我没有放宽 SQL 条件，而是加一个语义明确的参数，把"读谁的资料"和"题算在谁头上"这两件事拆开，
> 并且 owner_id 只允许流向检索路径，不允许流向写入路径。」

## 3. Docker 部署踩坑（讲工程能力，不是讲配置）

这一段的价值在于**每个坑都是真实排障**，能体现方法论。按"现象→误判→真因→定位手段"讲。

### 坑 1：大陆拉不到 Docker 官方镜像

- 现象：`get.docker.com` 脚本 `Connection reset`；`docker compose up` 报 `python:3.11-slim: not found`
- 真因：装 Docker 走的是被干扰的官方源；配了阿里云**个人**加速器后，个人源镜像覆盖不全，
  对 `python:3.11-slim` 这个 tag 直接返回 not found
- 解法：apt 源换阿里云 `mirrors.aliyun.com/docker-ce`；`/etc/docker/daemon.json` 里
  **DaoCloud 做主、阿里云做辅**（DaoCloud 覆盖全，阿里云速度快）
- 可讲的点：镜像加速器不是配一个就完事，要理解"个人版加速器只加速你拉过的"这类限制

### 坑 2：端口被同机另一个项目占用

- 现象：backend 起不来
- 定位：`ss -tlnp` 发现 `127.0.0.1:8000` 已被现有项目的 python 进程占用
- 解法：宿主机端口改 **8010**，容器内仍 8000，映射写 `127.0.0.1:8010:8000`
- 顺手的安全设计：**后端端口只绑 127.0.0.1，不对公网开放**，外部只能经 Nginx 反代 `/api/` 进；
  MySQL 完全不映射端口，只在 Docker 内网

### 坑 3：登录 401，一开始的误判（最值得讲）

- 现象：前端页面正常、`/api/v1/health` 正常，但登录恒 401
- **我的误判链**：先怀疑 MySQL 密码不一致 → 又以为服务器上代码是旧版、缺密码哈希函数
  → 甚至多跑了一次镜像重建（纯属浪费）
- 真因：那个管理员账号的 `password_hash` 与本项目 `hash_password` 不配套
- 定位手段其实很轻：`SELECT LEFT(password_hash,30), LENGTH(password_hash) FROM users`
  —— `$2b$12$` 开头、长度 60 才是本项目的正常产物
- 教训（我写进了项目总结）：**断言"代码缺失"之前先 grep 本地仓库找真实实现**。
  一个 `ImportError` 不等于功能没写，更可能是我自己 import 错了模块——
  本项目密码哈希在 `app/core/password.py`，而 `app/core/security.py` 只做敏感词过滤

### 坑 4：整页白屏，但接口全正常

- 现象：登录页空白，`/api/v1/health` 却返回正常
- 真因：用宝塔文件管理器框选 `dist` 下的文件上传，**只传上了根级 3 个文件，`assets/` 子目录没带上**，
  `index.html` 引用的 `assets/index-<hash>.js` 404
- 解法：整包 zip 上传后解压；核对 assets 里的 hash 与 index.html 引用一致；验收前 Ctrl+F5
- 可延伸：Vite 产物带内容 hash，所以 `expires 1y` 是安全的；但 `index.html` 本身不能缓存

### 坑 5：下拉框显示 ID 而不是名称

- 现象：数据都加载出来了，只有筛选下拉框显示 `asmt_xxx`
- 真因：后端所有分页接口是 `Query(10, ge=1, le=50)`，前端传了 `page_size=100` → 422
  → 被 `.catch(() => {})` **静默吞掉**，options 空数组，Select 只能回显原始 value
- 可讲的点：这不只是个数字写错，而是**静默 catch 把一个 5 分钟能定位的问题变成了 20 分钟**。
  我在手册里给自己留了话：联调阶段至少临时打印一次错误

### 坑 6：宝塔面板"域名"框三条校验

填 `IP:端口` 报端口不合法、填纯数字报格式错误、填已被占用的 IP 报已存在。
真因是那个框只做站点标识，Nginx 实际按 `listen` 端口 + `server_name` 匹配，
所以建站点时填占位子域名、再去配置文件补真实 `server_name` 即可。

## 4. 面试官大概率会追问的问题

**Q：为什么用 ChromaDB 而不是 Milvus / 阿里云向量检索服务？**
A：单机演示场景下 Chroma 零运维、本地持久化，而且 collection 粒度天然能做每用户一个的租户隔离，
`delete(where={"doc_id":...})` 删文档时级联清得干净。
**边界我也清楚**：数据在 `./data/chroma` 本地文件，多实例无法水平扩展，真要上规模得换托管向量库
或至少换成共享存储 + 分布式实现。

**Q：AI 生成题目质量不稳定怎么办？**
A：现在是 prompt 约束（题型 3:1:1、难度注入、取值域、多选≥2 个）+ Pydantic `Literal` 硬校验，
不合格直接报错。**但缺重试**，这是我列在待办第一位的改进——
上 `with_structured_output` 让模型走 function calling，再加 `with_retry`，比现在靠正则剥 markdown 壳稳。
另外代码不校验题型比例分布，只校验单题字段合法，这点也可以补。

**Q：怎么防员工绕过前端改答案？**
A：标准答案只存在服务端 `questions_json`，接口不返回给答题页；判分在服务端做精确比较。
前端能改的只有"选了哪个"，改不了"哪个对"。

**Q：JWT 放 role 会不会被篡改提权？**
A：HS256 签名保护，改 payload 会导致验签失败。而且 `get_current_admin` 不是只看 token 里的 role，
它 `get_current_web_user` 会**回查数据库**校验账号存在和 status（`auth.py:80-84`），
所以管理员把员工停用后，即使 token 没过期也立刻失效。

**Q：这项目的并发瓶颈在哪？**
A：几个层次。① 出题是 LLM 调用，秒级且占内存少，瓶颈在上游模型 QPS 和配额，不在我的服务；
② `asyncio.create_task` 处理文档入库是**进程内**的，多 worker 部署时任务归属会乱，这是明确的设计债；
③ Chroma 本地文件读写，多实例会打架。
所以横向扩容前必须先做：入库任务外置队列 + 向量库换共享服务。

**Q：如果重做一遍会改什么？**
排序：① 报告生成与成绩提交解耦（现在报告挂了会让整次提交 500，成绩也丢）；
② 加 LLM 输出重试和结构化输出；③ 分块改成标题感知；④ 检索加阈值和 rerank；
⑤ 早期那个"以为代码过期"的误判，说明我缺一个部署后自检脚本——
上线时自动跑一遍 health + 登录 + 检索冒烟，而不是靠人肉点页面。

## 5. 讲这些之前请先自测

面试现场如果演示，提前确认：

1. 演示地址在你**当前网络**能打开（IP 白名单失效是头号杀手，处置见部署手册 §11.1）
2. `admin` 账号能登录（口令已改，别再写进任何公开材料）
3. 提前跑一次完整链路，把「培训资料已就绪 / 一份答题复盘报告」的截图存本地——
   万一现场网络不通，还有图可讲
